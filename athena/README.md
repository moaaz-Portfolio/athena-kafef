# WiFi Radar — استشعار التواجد والحركة عبر Wi-Fi CSI

تستقبل وحدة ESP32-S3 بيانات Wi-Fi CSI وترسلها إلى وحدة معالجة محلية. تطبيق WiFi Radar يحلل الإشارة لعرض التواجد المحتمل والحركة وتصنيف النشاط، ويعرض اشتباه السقوط بعد توفر نموذج مدرّب. الواجهة تدعم العربية والإنجليزية وهوية Clean Research.

> المشروع نموذج بحثي وتجريبي. تنبيهات التواجد والسقوط تقديرية وليست جهازًا طبيًا أو نظام إنقاذ. لا تعتمد عليها لحماية شخص أو استبدال الإشراف البشري.

## النسخ

### Factory Edition

نسخة المصنع/البحث، وتسمح بتسجيل بيانات CSI، وتنظيمها بحسب النشاط والشخص والغرفة، ومراجعة التسجيلات، وتدريب النموذج، وفحص المقاييس.

من مجلد athena:

    pip install -r requirements.txt
    python -m athena --edition factory

### User Edition

نسخة التشغيل اليومي بعد إصدار النموذج المدرّب. تعرض المراقبة والمعايرة والسجل والإعدادات، وتمنع تسجيل البيانات والتدريب من الواجهة ومن واجهة API. المعايرة تخزن Room Profile منفصلًا ولا تعيد تدريب النموذج.

من مجلد athena:

    pip install -r requirements.txt
    python -m athena --edition user --host 0.0.0.0

استخدم 0.0.0.0 فقط على شبكة محلية موثوقة حتى يتصل الهاتف. لا تفتح منفذ التطبيق على الإنترنت ولا تستخدم تحويل منافذ الراوتر. التطبيق الافتراضي يستمع على 127.0.0.1.

## تشغيل ESP32-S3

1. من إعدادات فيرموير ESP32-S3 اختر دور CSI stream to PC.
2. تأكد أن ESP32-S3 ووحدة المعالجة على نفس الشبكة.
3. اسمح باستقبال UDP على المنفذ 5005 في الجدار الناري.
4. افتح لوحة WiFi Radar وتأكد من ظهور اتصال CSI ومعدل الإطارات.

البث الحالي يتضمن 64 قيمة amplitude لكل إطار. مواصفات الحزمة موضحة في نهاية هذا الملف.

## Factory Training Workflow

الحالات الأساسية المطلوبة لإصدار المستخدم:

| الفئة | اسم تسجيل مقترح | المقصود |
|---|---|---|
| Empty Room | empty | الغرفة فارغة |
| Person Static | sitting_still | شخص موجود وساكن |
| Movement | walking أو movement | حركة بشرية |
| Fall | fall | محاكاة سقوط آمنة تحت إشراف |

يلزم 3 تسجيلات مستقلة على الأقل لكل فئة كي يبدأ خط التدريب الحالي؛ وهذا حد تقني أدنى وليس حجمًا بحثيًا كافيًا. يُفضّل تسجيل عدد أكبر بكثير، عبر أشخاص مختلفين وغرف وأيام وأوضاع مختلفة.

أدخل مع كل تسجيل معرف الشخص والغرفة. لا تخلط تسجيلات شخص أو غرفة واحدة بين التدريب والاختبار عند تقييم التعميم. استخدم أدوات cross-validation لاختبارات ترك غرفة أو شخص خارج التدريب، وسجّل النتائج الفعلية.

### تصدير User Edition

بعد التدريب، يتطلب المُصدّر:
- نموذج activity_model.pt.
- ملف metrics.json من الاختبار.
- وجود فئات empty room وperson static وmovement وfall (تُقبل الأسماء البديلة المحددة في حزمة التصدير).
- مراجعة الباحث لنتائج كل فئة وConfusion Matrix والإنذارات الكاذبة.
- موافقة صريحة من الباحث على إصدار الحزمة.

من مجلد athena:

    python -m athena.package_user --version 1.0.0 --researcher-approved

ينشئ ذلك dist/WiFi-Radar-User.zip، ويستبعد بيانات المصنع وأدوات التدريب. لا يقوم المُصدّر باعتماد دقة النموذج تلقائيًا.

## معايرة الغرفة

- Factory Edition يستخدم معايرة قصيرة لأغراض الاختبار فقط.
- User Edition يجمع Room Profile لمدة 10 دقائق.
- يجب أن يصل 15 إطار CSI في الثانية على الأقل في المتوسط خلال المعايرة.
- تُرفض المعايرة إذا كان عدد الإطارات أو تغطية الوقت غير كافٍ، أو ظهرت تغيّرات كبيرة في خط الأساس بين أجزاء الجلسة.
- يجب أن تكون الغرفة فارغة وثابتة، ويجب عدم تحريك الراوتر أو اللوحة أثناء المعايرة.
- Room Profile ليس نموذج ذكاء اصطناعي ولا يعوض عن تدريب المصنع.

## التطبيق وإعدادات الإشعارات

يتم حفظ إعدادات الإشعارات على وحدة المعالجة المحلية لتكون مشتركة بين لوحة الويب وتطبيق Android. إيقاف نوع إشعار لا يوقف اكتشاف الحالة أو تسجيلها في سجل الأحداث.

لتوصيل Android:
1. افتح لوحة الويب محليًا على جهاز المعالجة.
2. انسخ رمز الربط الذي تعرضه اللوحة.
3. أدخل عنوان جهاز المعالجة ورمز الربط داخل تطبيق Android.
4. احفظ الإعدادات وشغّل خدمة الإشعارات.

يعمل التنبيه المحلي عندما يكون الهاتف وجهاز المعالجة على الشبكة المحلية نفسها. الإشعارات خارج الشبكة المحلية تحتاج إنترنت وخدمة توصيل Push مناسبة؛ التطبيق الحالي يعتمد على فحص API المحلي كل 3 ثوانٍ.

## وحدة الباب

حساس الباب مخطط له كعقدة منفصلة: ESP32 + HC-SR04 + Buzzer. لم يكتمل ربط هذه العقدة بعد. الحساس الواحد يستطيع رصد وجود جسم في مجال القياس، لكنه لا يثبت اتجاه الدخول أو الخروج. إعداد Buzzer موجود كخيار محفوظ في الإعدادات إلى حين اكتمال ربط عتاد الباب.

## اختيار جهاز المعالجة

ESP32-S3 مسؤول عن جمع/إرسال CSI. نموذج CNN + BiLSTM الحالي يستخدم PyTorch؛ لذلك لا نفترض أنه سيعمل مباشرة على ESP32-S3. يجب اختيار جهاز معالجة ثابت (مثل Raspberry Pi مناسب أو Mini PC) بعد قياس وقت الاستدلال واستهلاك الذاكرة والحرارة والتشغيل المتواصل على checkpoint الحقيقي.

المستخدم النهائي لا يحتاج لابتوب تطوير أثناء التشغيل اليومي إذا ثُبّتت وحدة المعالجة ضمن النظام.

## تقييم علمي وسلامة

- اختبر على أشخاص وغرف لم تظهر في بيانات التدريب.
- اعرض Precision وRecall وF1 لكل فئة، لا Accuracy وحدها.
- سجّل False Positives وFalse Negatives.
- استخدم أمثلة سلبية مثل الجلوس والانحناء والاستلقاء وسقوط جسم.
- لا تنفذ سقوطًا حقيقيًا لجمع البيانات؛ استخدم محاكاة آمنة متحكمًا بها على سطح لين وتحت إشراف بالغ.
- لا تستخدم النظام كجهاز طبي أو إنذار إنقاذ.

## ملفات مهمة

- athena/app.py: خادم الويب، الـ API، وإدارة النسختين.
- athena/edition.py: إعدادات النسخة وإعدادات الإشعارات.
- athena/receiver.py: استقبال UDP.
- athena/data.py: حفظ التسجيلات وتجهيز النوافذ.
- athena/model.py وathena/train.py: النموذج والتدريب.
- athena/live.py: الاستدلال على البث.
- athena/monitor.py: معايرة الغرفة ومؤشر التواجد ومنطق اشتباه السقوط.
- package_user.py: إصدار حزمة المستخدم.
- EDITION_WORKFLOW.md: خطوات الإصدار بالتفصيل.

## صيغة CSI Stream

حزمة UDP بترتيب Little-endian:
- ASCII "CSI1"
- seq: uint32
- ts_ms: uint32
- rssi: int8
- n: uint8
- amp[n]: uint8

المنفذ الافتراضي 5005.
